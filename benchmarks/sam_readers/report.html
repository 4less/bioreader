What was measured

Every contender walks the whole file and, for each alignment record, sums SEQ length + POS + the NM tag — one length, one integer field and one optional-field lookup, so no implementation can win by skipping work. Each returns a checksum and a record count, and the harness asserts every implementation produces the same pair. All rows below passed that check.

Both files are synthetic but realistically shaped: an 8-line header, ~5% unmapped records and five optional fields (NM MD AS XS RG) on every mapped record. The page cache is warmed before timing, so these are parser numbers, not disk numbers.

Both readers are compared at their own best buffer setting — bioreader at 1 MiB batches, noodles at a 256 KiB BufReader — found by the sweep further down. The naive baseline is what a straightforward implementation looks like: read a line, split on tabs, str::parse.

Short reads — 1.58 GB, 4M records of 150 bp

Long reads — 1.21 GB, 60k records of 10 kb

This is the one shape where noodles wins, and the reason is structural rather than a parsing detail. With 10 kb records there are only 60,000 of them: per-record overhead is irrelevant and what remains is how many times each byte is touched. noodles copies each line into a reused record buffer that stays hot in L2; bioreader copies a whole batch out of the shared reader so workers can parse without holding the lock, and that second pass over cold memory costs the 10 ms.

Threads do not help here either — 1 thread (14.09 GB/s) beats 8 (9.94 GB/s) through the parallel driver, because there is no per-record work to parallelise and the extra threads only add copy traffic. For long-read files with light per-record work, use one thread; the moment the closure does real work per record, scaling returns.

Batch size is the biggest single knob

Both readers copy every byte through a buffer, so whether that buffer stays in cache dominates everything else. The reader was first measured at 16 MiB batches, which turned out to be the worst setting tested on both files. At 1 MiB the short file gets 25% faster and the long file 2.3× faster.

What the extra features cost

Regression floor

These medians are now a floor the reader is checked against, at 85% of the measured value — enough headroom for run-to-run noise on a boosting laptop CPU (the multithreaded rows swing about ±10%), tight enough to catch a real regression. Each floor records the baseline it came from, so re-baselining is a deliberate edit rather than a quiet drift.

Reproduce it

# benchmarks/sam_readers
cargo build --release

# synthetic data: 4M x 150 bp, and 60k x 10 kb
./target/release/gen short.sam 4000000 150
./target/release/gen long.sam    60000 10000
pigz -1 -k short.sam                 # optional, adds the gzip rows

# full report: batch-size sweep, then the comparison
./target/release/sambench short.sam 5

# regression floor — exits 1 if anything drops below
./target/release/sambench --check short short.sam 3
./target/release/sambench --check long  long.sam  3

Floors live in SHORT_FLOORS / LONG_FLOORS in benchmarks/sam_readers/src/main.rs. The harness verifies all implementations agree on the checksum before reporting any timing, so an implementation that gets fast by doing less fails instead of winning.
